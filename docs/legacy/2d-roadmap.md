# 微风小镇 V1：长期路线图与 Agent 任务包

版本：0.3；日期：2026-09-08  
状态：用户已授权启动 M0；按 `05-execution-readiness.md` 的已填任务卡执行，M1–M6 逐阶段细化。实际进度以 `docs/execution/task-board.md` 为准，本文定义任务而非通过结果。

## 1. 怎样分派

先指定一个 LEAD。角色是职责，不是必须同时开九个 agent；建议一名负责人管理 3–5 个同时进行的实现任务。用户负责重大产品取舍，LEAD 负责已有范围内的技术选择、验收和集成。

每次只发一个任务 ID、依赖版本和具体写入范围。未通过依赖门禁时，可读文档或制作独立样例，不得把自创接口合入主工程。M0 技术验证可以直接开始，不要求用户先逐项批准全部默认数值。

### 1.1 角色与唯一所有权

代码路径相对将来的 Godot 工程根 `game/`；`docs/`、`tools/`、`work/` 相对仓库根。本文提到的路径是计划结构，目前没有游戏工程。

六份需求基线当前位于项目根目录；分派时直接读取这些实际文件，不先复制到 `docs/`。本节是长期模块所有权，`05-execution-readiness.md` 为 M0 另列任务专用实验/报告路径，权限只在对应任务内有效。

| 角色 | 唯一写入范围与职责 | 不能自行修改 |
|---|---|---|
| LEAD | 仓库元文件、CI、docs/adr 的决策索引、任务状态、跨模块集成审批 | 其他角色代码；应通过 owner 修复或先明确移交 |
| FND | project.godot、export_presets.cfg、src/bootstrap/、scenes/bootstrap/、src/contracts/、content/schema/、tests/unit/contracts/ | 农务/经济规则；所有共享契约变更须由 LEAD 审阅 |
| SIM | src/domain/world/、src/application/core/、src/application/world/、tests/unit/simulation/ | 文件存储和网络实现 |
| FARM | src/domain/farming/、src/domain/projects/、对应 application/farming 和 projects、content/definitions/crops 和 projects、tests/unit/farming/ | 库存容器内部、经济定义和统计投影 |
| ECON | domain/inventory、economy、statistics，application/inventory、economy、reporting/stats，definitions/items、shop，tests/unit/economy/ | 农务/项目定义、公开导出器 |
| NET | infrastructure/network、identity，application/session、sync，tests/network/ | WorldState、业务规则、私有存档格式 |
| DATA | infrastructure/persistence、public_export，application/reporting/public，tests/unit/data/，tools/migration/ | 统计计分、共享 schema 原文件 |
| UI | src/client/、scenes/client/、assets/、content/maps/、tests/client/、docs/ui/ | 权威状态和冻结 schema；地图必须通过 FND schema 校验 |
| QA | tests/integration、acceptance、performance、security、fixtures，tools/test、release，docs/testing、reports/ | 各 owner 的单测目录、实现代码和产品门槛 |

路径缩写沿用同一 src/ 或 content/ 前缀，不表示另建第二个根目录。任务表给出输出主题，具体改动仍受上表约束。接口缺失时由 FND 修改契约，调用方不可直接越界。

一名角色的多个任务默认顺序执行；要拆给两名 agent，LEAD 必须先分出互不重叠的文件列表。同一世界模型、bootstrap、项目配置、schema、公共 fixture 不能多人双写。

### 1.2 合作规则

- 使用独立目录/worktree 或经授权的分支；不自动创建分支、提交、推送或覆盖别人的未合并改动。
- 实现者写本模块有价值的单测；QA 写跨模块验收和故障测试，两者不争抢同一测试文件。
- FND 维护共享类型，其他角色使用冻结版本；需要更改先提出 ADR，得到技术裁决后再集成。
- 里程碑允许同阶段内部按依赖逐步集成，不必等所有任务全做完才发现组合失败。
- 构建包、真实存档、私钥、凭据、原始抓包不入源码库。合法且允许再分发的精选第三方素材可按许可登记入库，下载缓存不入库。
- 核心规则不能通过 UI 或网络适配器补丁“修好”；修复应回到相应领域 owner。
- LEAD 审阅代码和证据后才把任务置为 ACCEPTED；agent 自报完成对应 REVIEW，不能直接表示里程碑通过。

## 2. 长期节奏与阶段门禁

以下是排期参考，不是承诺工期。假设有持续集成负责人、3–5 个有效并行任务、双平台测试条件和可合法使用的素材；AI 执行时间不能直接按 agent 数量等分。

| 阶段 | 参考时间 | 可演示结果 | 出口条件 |
|---|---|---|---|
| M0 风险验证与契约 | 1–2 周 | 最小握手、headless、保存故障试验 | 明确网络路线、精确引擎版本、接口 fixture、平台资源和存档发布方案 |
| M1 单人完整循环 | 2–3 周 | 创建→移动→播种→浇水→日切→收获→出售→三榜→保存/继续 | 一条真实组合路径通过，规则可无界面测试 |
| M2 房主联机 | 2–3 周 | A 开服、B/C/D 加入、移动、重连 | 身份/版本/快照/差量/序号正确；无 UI 权威绕路 |
| M3 多人完整玩法 | 2–3 周 | 五作物、仓库、三建设、救济、并发与榜单 | 四人真实流程通过，跨日/抢收/重复命令无重复结算 |
| M4 数据与公开交付 | 2–3 周 | 恢复、导出、迁移到 headless 后继续 | 故障/授权/版本/搬迁全部有证据 |
| M5 体验与优化 | 2–4 周 | 统一素材、引导、双平台候选包 | NFR 实测、长稳、跨平台黑盒通过 |
| M6 封闭验收发布 | 1–2 周 | 五名新手反馈、0.1.0 包与手册 | 阻断/严重缺陷清零，发布证据归档 |

串行区间约 12–20 周；素材、平台签名、真实网络或测试者不足时另留 25%–35% 缓冲。M0 后用实际完成速度重估，不给尚未测量的任务报具体完成日期。流水线可重叠，但不能跳过出口条件。

### 2.1 M0 的验证门，不等于实现所有后续功能

- FND-01：精确 Godot/导出模板版本，四种启动组合的空壳，无 UI 的 headless smoke。
- FND-02：最小状态、命令、事件、错误码、版本、公开 DTO 和地图/内容 schema fixture。
- NET-01：独立样例中的可信加密握手、新成员批准/重复身份/四席位及失败实验。
- DATA-00：独立样例中的写锁、代际发布、破坏最新代/未来格式测试。
- QA-01：测试框架、执行命令、网络仿真方式、最低机和目标平台资源登记。
- UI-01：菜单/加入/HUD/榜单/错误/公开的流程草图和输入焦点契约。
- LEAD-01：收集上述证据并冻结路线。独立样例不是正式玩法或安全认证，M1–M4 仍需集成回归。

NET-01 的加密路线先限 3 个工作日做证据/风险报告；不成立则由 LEAD 对 TLS/WebSocket 后备做一次有记录的选择，不能无限试验或直接明文降级。真实网络/目标平台缺失可以记录阻塞并推进无关工作；未验证的网络路线不能宣称可发布。

### 2.2 M1–M6 每阶段必须具备

- M1：最小移动、静态碰撞、基础游戏日和基础自动/手动/退出保存都在本阶段，不能等待 M2/M3 才补齐闭环。
- M1：NET-00 实现本地身份，创建世界即持久保存所有者凭据；UI-02/INT-01 集成验收，不以硬编码 owner ID 替代。SIM-01 使用 FND-02 的地图 schema 样例，正式地图由 UI-02 接入。
- M2：四名玩家包含房主；dedicated 没有虚拟房主占席。协议不匹配、重复身份、重连中未确认命令有测试。
- M3：日切屏障和仓库/建设在多人情况下正确；所有数据定义按各 owner 唯一维护。
- M4：公开与私有数据使用不同 DTO；显式回退旧备份后的重新绑定和重新同意流程通过。
- M5：发布构建在 Windows x64/macOS Apple Silicon 实机测试；性能报告同时记录机器和配置。
- M6：五名新手测试只在这里执行正式验收，M5 可做内部试用；外部分发由用户或有明确发布授权的人执行。

## 8. 统一完成定义与变更控制

每项 ACCEPTED 必须满足：

- 功能在声明模式下实际运行；不能用 mock 通过推断真实进程通过。
- 相关领域失败/并发/重发用例通过，UI 不直接改权威数据。
- 共享契约、内容 hash、存档和公开字段一致，新增依赖有许可记录。
- 代码已经通过负责人集成验收；无任务内已知阻断/严重问题。
- 用户文档与工程行为一致；说明未覆盖的平台/网络/性能限制。

新增玩法、改变世界模型、公开字段、计分或发布平台时，提出 ADR：原因、影响 FR/NFR/任务/CASE、预计成本、替换/延后的工作、迁移和测试方案。既有范围内可逆实现选择由 LEAD 判断；用户级产品范围变化再找用户，不将所有普通代码决定都变成审批。

禁止在 V1 偷渡 NPC、钓鱼、付费、全球官方榜、中继运营或微服务。V1.1 优先候选是正式自建服包装与备份运维；是否增加新玩法以真实反馈和用户后续 idea 为准。
